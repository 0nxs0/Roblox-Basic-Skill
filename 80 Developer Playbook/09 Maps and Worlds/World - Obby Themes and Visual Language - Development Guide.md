# World - Obby Themes and Visual Language — Development Guide

New practical guidance for [[09 Maps and Worlds/Maps/Community Knowledge/World - Obby Themes and Visual Language|World - Obby Themes and Visual Language]]. This companion adds a build and validation plan; use the linked source for full reference detail.

## Source-grounded context
Obby players judge a game from the thumbnail and the first three stages, and the theme is what makes one obby different from a thousand others. But a theme must never hide the rules: every theme needs the same visual language for "safe", "deadly", "moving" and "checkpoint". This note is about theming worlds; stage difficulty and checkpoints are in the obby stage note.
**Useful source sections:** The fixed language (keep across every theme), Theme recipes (world = 8-15 stages), Layout per world.

## Apply it
Use this topic as part of **shape navigation within runtime budgets**.
- **Define the contract:** For World - Obby Themes and Visual Language, write down behavior, inputs, state owner, visible result, and failure response.
- **Build a first slice:** Set a traversal goal and landmark rhythm; test a greybox route before adding detail.
- **Maintain it:** Separate tuning data from behavior, record assumptions, and provide cleanup or rollback before connecting more systems.
- **Project risk:** Plan streaming, spawns, sightlines, collision, accessibility, and memory together.

## Validate before shipping
- **Expected path:** Build one small feature using World - Obby Themes and Visual Language and record setup and expected result.
- **Boundary case:** Test missing, invalid, repeated, delayed, or interrupted input where relevant.
- **Integration:** Test with neighboring systems and at target device/player scale.
- **Acceptance check:** Test route clarity, streaming, respawn recovery, and low-end rendering.
